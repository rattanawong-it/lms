## 2. ลำดับงาน (ขั้น 0 + 6 ขั้น · ขั้น 7 DRM ถ้าเลือก)

เรียงตามการพึ่งพา: ราคาต้องมีก่อนชำระเงิน · ชำระเงินต้องมีก่อนคูปอง/ใบเสร็จ/คืนเงิน · หยุดให้ตรวจที่จุด ✋
ทุกขั้นพัฒนากับ **ผู้ให้บริการจำลอง (mock provider)** ได้ก่อน แล้วค่อยต่อ sandbox จริงเมื่อได้บัญชี — e2e ไม่ยิงเงินจริง/ไม่ต้องใช้อินเทอร์เน็ต

### ขั้น 0 — โครง payment adapter + mock (1 วัน) — ✅ เสร็จ 2026-09-25
- `src/lib/payment/` — จุดเดียวที่รู้จักผู้ให้บริการ (เหมือน `storage.ts` รู้จัก S3)
  ```
  lib/payment/
    index.ts        getPaymentProvider() ตาม env PAYMENT_PROVIDER
    types.ts        createCheckout() · retrieve() · refund() · verifyWebhook()
    providers/mock.ts       หน้าชำระเงินจำลองในแอป (เฉพาะ dev/test — ปิดใน production)
    providers/<จริง>.ts     ตาม Q1
  ```
- จำนวนเงินส่งให้ gateway เป็นหน่วยสตางค์ (จำนวนเต็ม) · คำนวณจาก `Decimal` ฝั่ง server เท่านั้น
- env ใหม่ (ไม่บังคับ): `PAYMENT_PROVIDER`, `PAYMENT_SECRET_KEY`, `PAYMENT_PUBLIC_KEY`, `PAYMENT_WEBHOOK_SECRET` — ไม่กำหนด = ปิดการขาย (คอร์สที่มีราคาแสดง "ยังไม่เปิดขาย")

**สิ่งที่ทำจริง:** `src/lib/payment/{index,types,money,guard}.ts` + `providers/mock.ts` (สถานะเก็บในหน่วยความจำ · webhook เซ็น HMAC-SHA256 ด้วย `PAYMENT_WEBHOOK_SECRET` ใน header `x-mock-signature`)
· env `PAYMENT_PROVIDER` (ตอนนี้รับ `mock` — `omise` เพิ่มในขั้น 2) · `hasPayment` · production + mock ไม่ยอมเริ่ม เว้นแต่ `ALLOW_MOCK_PAYMENT=true` (สำหรับ `next start` ของ Playwright)
· `/admin/settings` แสดงสถานะการชำระเงิน · unit `payment.test.ts` (สตางค์, ลายเซ็น, หมดอายุ, คืนเงิน, ตัวกัน production)
· **แก้บั๊กจาก Phase 3 ที่ e2e จับได้:** อนุมัติ/ปฏิเสธคำขอลบบัญชีกดซ้อนแล้วทำงานสองครั้ง (audit 2 แถว) → จองคำขอด้วย `updateMany` แบบมีเงื่อนไขก่อนเริ่มงาน

### ขั้น 1 — ตั้งราคาและแสดงราคา (FR-18.1 ส่วนแรก) — ✅ เสร็จ 2026-09-25
- ฟอร์มคอร์ส: ช่อง "ราคา (บาท)" เฉพาะคอร์ส `PUBLIC` · ว่าง/0 = ฟรี · ผู้ตั้งราคาตาม Q3
- catalog + หน้าคอร์ส: ป้ายราคา/"ฟรี" · ปุ่ม "ซื้อคอร์ส ฿x" แทน "ลงทะเบียน" เมื่อมีราคา
- `enrollSelf()` ปฏิเสธคอร์สที่มีราคา (deny by default — กันยิง action ตรง) · ผู้ดูแลยังเพิ่มผู้เรียนเข้าคอร์สที่มีราคาได้ (`source = ADMIN`) เช่นทุนการศึกษา
- **Test:** unit กติกา "คอร์สนี้ต้องซื้อไหม" · e2e ผู้เรียนเห็นราคาและกดลงทะเบียนฟรีไม่ได้แม้ยิง action ตรง

**สิ่งที่ทำจริง:** `features/commerce/lib/pricing.ts` (pure: `isPaidCourse()` · `canEditPrice()` · `parsePriceInput()` · `courseOffer()`) · ช่อง "ราคา (บาท)" ในฟอร์มคอร์ส (ล็อกเป็น disabled → server คงราคาเดิม)
· การ์ด catalog ป้ายราคา/"ฟรี" (คอร์สภายในไม่มีป้าย) · หน้าคอร์ส `PurchasePanel` แทนแผงลงทะเบียน (ยังไม่ต่อ gateway / คอร์สไม่ใช่ OPEN → "ยังซื้อไม่ได้") · `enroll()` ปฏิเสธคอร์สที่มีราคา
· คิว `/admin/courses` แสดงราคาที่เสนอ · migration S6 `Course_price_check` · seed `excel-for-work` (990 บาท) · audit `course.create/update` มีราคา
· **ปรับจากแผน:** คอร์สที่มีราคาแต่รับสมัครแบบขออนุมัติ/เชิญเท่านั้นไม่เปิดให้ซื้อ (ให้ผู้ดูแลเพิ่มผู้เรียนเอง) · e2e ข้อ "ยิง action ตรง" ตรวจด้วย unit ของ `isPaidCourse()` + การไม่มีปุ่ม (Playwright เรียก Server Action ตรงไม่ได้)
· unit `pricing.test.ts` · e2e `pricing.spec.ts` (support/pricing-fixture)

### ขั้น 2 — สั่งซื้อและชำระเงิน (FR-18.1) — 🔸 เสร็จกับผู้ให้บริการจำลอง 2026-09-25 · Omise รอ sandbox · ✋ *จุดตรวจที่ 1*
- `/checkout/[courseId]` สรุปรายการ → สร้าง `Order` PENDING (ราคาจาก DB ณ ตอนนั้น) → ส่งไปหน้าชำระของผู้ให้บริการ (บัตร + PromptPay)
- **ยืนยันผลที่ webhook เท่านั้น** `/api/payment/webhook/[provider]`
  1. ตรวจลายเซ็น → 2. ดึงสถานะจาก API ของผู้ให้บริการซ้ำ (ไม่เชื่อ payload) → 3. บันทึก `PaymentEvent` (กันประมวลผลซ้ำด้วย unique event id)
  4. transaction เดียว: `Order` → PAID · สร้าง/เปิด `Enrollment` (`PURCHASE`) · ตัดสิทธิ์คูปอง → 5. `notify()` + audit
- หน้ากลับจาก gateway `/orders/[orderId]` แสดง "กำลังตรวจสอบการชำระเงิน" แล้ว refresh จนสถานะเปลี่ยน (ไม่ตัดสินจาก query string)
- กันซื้อซ้ำ: มีคำสั่งซื้อ PENDING ที่ยังไม่หมดอายุ → ใช้อันเดิม · ลงทะเบียนอยู่แล้ว → ไม่ให้ซื้อ
- คำสั่งซื้อ PENDING หมดอายุใน 30 นาที (QR PromptPay) → cron cleanup ตั้ง FAILED
- `/orders` — ประวัติการสั่งซื้อของฉัน
- **Test:** unit คำนวณยอด/สตางค์ · ตรวจลายเซ็น · idempotency (webhook ซ้ำ 2 ครั้ง = ลงทะเบียนครั้งเดียว) · e2e ผ่าน mock provider: ซื้อ → เข้าเรียนได้ · จ่ายไม่สำเร็จ → ยังเข้าไม่ได้
- ✋ **จุดตรวจที่ 1:** ทดสอบกับ sandbox ของผู้ให้บริการจริง (บัตรทดสอบ + PromptPay ทดสอบ) บน Chrome

### ขั้น 7 — DRM วิดีโอ (ทางเลือก ตาม Q8)
- ถ้าเลือก: ย้ายวิดีโอคอร์สที่มีราคาไปผู้ให้บริการ DRM (Widevine/FairPlay — เช่น Mux, Bunny Stream, VdoCipher) ผ่าน adapter เดียวกับ storage
  · ต้องมีสัญญา/ค่าใช้จ่ายรายเดือน · กระทบหน้าเรียน, CSP, และขั้นตอนอัปโหลด → แยกเป็นแผนย่อยเมื่อได้ผู้ให้บริการ
- ถ้าไม่เลือก: คงการป้องกันแบบ M15 (ลายน้ำ + signed URL) ตามเดิม

## 6. ข้อที่ต้องการคำยืนยันก่อนเริ่ม — ตอบแล้ว 2026-09-25: ใช้ข้อเสนอทั้งหมด

| # | คำถาม | ข้อเสนอ (= คำตอบ) |
|---|---|---|
| Q1 | ผู้ให้บริการ payment gateway (D-05) | **Opn Payments (Omise)** — บริษัทไทย รองรับบัตร + PromptPay + โมบายแบงก์กิ้ง เงินเข้าบัญชีไทย เอกสารภาษาไทย · ทางเลือก: Stripe (หน้าชำระสำเร็จรูป ต้องมีนิติบุคคลในไทย) หรือ gateway ของธนาคารที่สถาบันใช้อยู่ — **ขอให้ฝ่ายการเงินยืนยันว่ามีสัญญากับเจ้าไหนอยู่แล้ว** · โค้ดทำผ่าน adapter จึงเปลี่ยนภายหลังได้ |
| Q2 | สถาบันต้องออก **ใบกำกับภาษี** ไหม (จด VAT หรือได้รับยกเว้นในฐานะสถานศึกษา) และต้องใช้ e-Tax Invoice หรือไม่ | ถ้ายกเว้น VAT → ออก "ใบเสร็จรับเงิน" อย่างเดียว ไม่เก็บข้อมูลผู้เสียภาษี · **ต้องให้ฝ่ายบัญชีตอบ** — กระทบรูปแบบเอกสารและฟิลด์ใน checkout |
| Q3 | ใครตั้งราคาและสร้างคูปอง · ผู้สอนเห็นยอดเงินไหม | ผู้สอนเสนอราคาในฟอร์มคอร์ส แต่ **มีผลเมื่อ DEPT_ADMIN/SUPER_ADMIN อนุมัติ** (ใช้ขั้นอนุมัติคอร์สเดิม) · คูปองสร้างได้เฉพาะผู้ดูแล · ผู้สอนเห็นจำนวนผู้ซื้อ ไม่เห็นยอดเงิน |
| Q4 | คอร์ส INTERNAL ขายได้ไหม | **ไม่ได้** — ราคาใช้กับ `PUBLIC` เท่านั้น (นักศึกษาเรียนคอร์สภายในฟรีตามเดิม) |
| Q5 | ซื้อแล้วเรียนได้นานเท่าไร | ตลอดไป (`expiresAt = null`) เป็นค่าเริ่มต้น · ถ้าต้องการกำหนดอายุต่อคอร์ส เพิ่ม `Course.accessDays` (schema เพิ่ม 1 คอลัมน์) |
| Q6 | นโยบายคืนเงิน | คืนเต็มจำนวนภายใน **7 วัน** และเรียนไม่เกิน **20%** (ผู้ดูแลกดคืนเองนอกเงื่อนไขได้พร้อมเหตุผล) · ไม่มีคืนบางส่วนในเฟสนี้ · คืนแล้วสิทธิ์เรียนถูกยกเลิก (`DROPPED`) · ใบประกาศที่ออกแล้ว**ถูกเพิกถอน** |
| Q7 | คูปองหมดสิทธิ์ระหว่างผู้ซื้อกำลังจ่าย | ยึดตามตอนสร้างคำสั่งซื้อ (จองสิทธิ์ไว้ 30 นาทีเท่าอายุคำสั่งซื้อ) — ผู้ซื้อไม่เจอยอดเปลี่ยนหลังจ่าย |
| Q8 | ทำ DRM ในเฟสนี้ไหม | **ยังไม่ทำ** — มีค่าบริการรายเดือนและต้องเปลี่ยนวิธีเก็บวิดีโอ · ตัดสินใจใหม่เมื่อมีคอร์สที่มีราคาจริงและเจอปัญหาการหลุดของวิดีโอ |
| Q9 | ยืนยันการเปลี่ยน schema S1–S6 และ route ใน §5 | — |
| Q10 | จุดหยุดตรวจ 2 จุด (หลังชำระเงินกับ sandbox และปิดเฟส) พอไหม | พอ — เหมือน Phase 1–3 |

**ยังต้องได้จากสถาบัน (ข้อเสนอ Q1/Q2 เป็นสมมติฐานจนกว่าฝ่ายการเงิน/บัญชียืนยัน):** Q2 ตั้งต้นเป็น "ใบเสร็จรับเงินอย่างเดียว ไม่มี VAT" ·  บัญชี sandbox ของ gateway (Q1) · คำตอบเรื่องภาษี (Q2) · ข้อมูลผู้ขายที่จะพิมพ์บนใบเสร็จ · ขั้น 0–1 เริ่มได้เลยโดยไม่ต้องรอ (ใช้ mock)

## 7. ความเสี่ยงที่มองเห็นตอนนี้

| ความเสี่ยง | ผลกระทบ | แนวทาง |
|---|---|---|
| ปลอมผลการชำระ (แก้ query string / ยิง webhook ปลอม) | ได้คอร์สฟรี | ตรวจลายเซ็น + ดึงสถานะจาก API ผู้ให้บริการซ้ำ · หน้า return ไม่ตัดสินผล |
| webhook มาซ้ำ/มาช้า/มาสลับลำดับ | ลงทะเบียนซ้ำ · สถานะย้อน | `PaymentEvent.eventId` unique · เปลี่ยนสถานะได้เฉพาะทิศทางที่อนุญาต (PENDING→PAID→REFUNDED) |
| จ่ายเงินแล้วแต่ระบบไม่ได้รับ webhook | ผู้ซื้อจ่ายแล้วเข้าเรียนไม่ได้ | หน้า `/orders/[id]` ถามสถานะจาก API ซ้ำได้ · cron ตรวจ PENDING ที่ค้างก่อนตั้ง FAILED · ผู้ดูแลกด "ตรวจสอบกับผู้ให้บริการ" ได้ |
| ราคาเปลี่ยนระหว่างผู้ซื้อกำลังจ่าย | เก็บเงินไม่ตรงราคา | ยอดล็อกใน `Order` ตอนสร้าง · gateway เก็บตามยอดใน Order |
| คูปองถูกใช้เกินจำนวน (race) | ขาดทุน | ตัดสิทธิ์ด้วย UPDATE แบบมีเงื่อนไขในทรานแซกชันเดียวกับการชำระ |
| เลขใบเสร็จซ้ำ/ข้าม | ผิดหลักบัญชี | `DocumentCounter` ในทรานแซกชันเดียวกัน · ไม่ลบใบเสร็จ (คืนเงินออกเอกสารใหม่) |
| ลบบัญชีตาม PDPA ชนกับหน้าที่เก็บเอกสารบัญชี | ผิดกฎหมายด้านใดด้านหนึ่ง | คงคำสั่งซื้อ/ใบเสร็จ (มีฐานทางกฎหมาย) ล้างเฉพาะข้อมูลที่ไม่จำเป็น — ยืนยันกับฝ่ายกฎหมายพร้อม Q2 |
| หน้าชำระเงินจำลองหลุดไป production | ได้คอร์สฟรี | env ตรวจตอนเริ่มระบบ: `NODE_ENV=production` + `PAYMENT_PROVIDER=mock` → ไม่ยอมเริ่ม |
